# Лабораторная работа 5 — транзакции, целостность данных и серверная логика

## Цель и результат

Показать атомарное оформление заказа, расчёт выручки PL/pgSQL-функцией и триггеры, которые ведут аудит цены и поддерживают средний рейтинг товара.

## Состав папки

- `00_schema_from_lab01.sql` — копия базовой схемы маркетплейса из `lab01`.
- `01_seed_data_from_lab02.sql` — копия тестового набора из `lab02`.
- `02_server_logic.sql` — поле рейтинга, таблица аудита, две прикладные функции и триггеры.
- `03_successful_transaction.sql` — успешное оформление заказа между `BEGIN` и `COMMIT` с запросом для просмотра результата.
- `04_failed_transaction_demo.psql` — намеренно неуспешный заказ и явный `ROLLBACK`; запускается через `psql`, который продолжает работу после ожидаемой ошибки.
- `05_trigger_demonstration.sql` — смена цены и отзыв для показа работы триггеров.
- `06_validation_queries.sql` — запросы для просмотра выручки, журнала и сохранённых рейтингов.
- `report.md` — краткий отчёт с обоснованием размещения логики и выводом.

## Как запускать

Создайте отдельную учебную базу `marketplace_lab05`: схема `marketplace` в файле `00_schema_from_lab01.sql` удаляется и создаётся заново только внутри неё. Выполняйте по порядку `00`, `01`, `02`, `03`, затем `04` через `psql`, `05` и `06`. Для `psql` из корня репозитория:

```text
createdb -U postgres marketplace_lab05
psql -U postgres -d marketplace_lab05 -v ON_ERROR_STOP=1 -f lab05/00_schema_from_lab01.sql
psql -U postgres -d marketplace_lab05 -v ON_ERROR_STOP=1 -f lab05/01_seed_data_from_lab02.sql
psql -U postgres -d marketplace_lab05 -v ON_ERROR_STOP=1 -f lab05/02_server_logic.sql
psql -U postgres -d marketplace_lab05 -v ON_ERROR_STOP=1 -f lab05/03_successful_transaction.sql
psql -U postgres -d marketplace_lab05 -f lab05/04_failed_transaction_demo.psql
psql -U postgres -d marketplace_lab05 -v ON_ERROR_STOP=1 -f lab05/05_trigger_demonstration.sql
psql -U postgres -d marketplace_lab05 -v ON_ERROR_STOP=1 -f lab05/06_validation_queries.sql
```

Если использовать pgAdmin, выполняйте сценарий неудачной транзакции `04` по частям: сначала `BEGIN` и `UPDATE`, затем запрос `SELECT place_order(...)`, который намеренно вызовет ошибку, и после появления ошибки выполните `ROLLBACK`. Не запускайте остальные команды транзакции из редактора после ошибки, пока не выполнен откат.

## Выполнение технического задания

1. `03_successful_transaction.sql` показывает успешную покупку: функция создаёт заказ и позицию, уменьшает остаток, а `COMMIT` фиксирует все изменения вместе.
2. `04_failed_transaction_demo.psql` сначала меняет остаток, затем вызывает функцию с количеством больше доступного. Ошибка переводит транзакцию в состояние сбоя; `ROLLBACK` отменяет и предшествующее изменение остатка. После него запрос показывает исходный остаток, а функция не создаёт заказ.
3. `place_order` использует локальные переменные, `SELECT ... INTO`, ветвления и `RAISE EXCEPTION`; условный `UPDATE ... WHERE quantity >= p_qty` не даёт складу уйти в минус при конкурирующих запросах. Если любой шаг не проходит, PostgreSQL откатывает оператор вызова целиком.
4. `seller_revenue_for_period` сохраняет сумму запроса в переменную и возвращает выручку одного продавца за интервал `[начало, конец)`. Считаются заказы со статусами `paid`, `processing`, `shipped` и `delivered`.
5. `product_price_audit` хранит старую и новую цену, время и пользователя, изменившего цену. У таблицы аудита намеренно нет внешнего ключа на товар, поэтому история не исчезнет вместе с карточкой.
6. Поле `products.rating` хранит среднее значение с точностью до двух знаков. Триггеры пересчитывают его после вставки, изменения оценки/товара отзыва и удаления отзыва.
7. В приложении уместны интерфейс, взаимодействие с пользователем и логика, зависящая от конкретного клиента. В БД уместны общие правила целостности, атомарные изменения связанных таблиц, аудит и вычисления рядом с данными. Серверная логика единообразна для клиентов, но сильнее связывает решение с PostgreSQL и требует отдельного тестирования и версионирования.

## Контрольные вопросы

1. **Что такое транзакция и каковы ACID?** Это группа операций как единое целое. ACID: атомарность, согласованность, изоляция и долговечность.
2. **Что делают `COMMIT`, `ROLLBACK` и `SAVEPOINT`?** `COMMIT` фиксирует изменения, `ROLLBACK` отменяет транзакцию, `SAVEPOINT` задаёт точку для частичного отката.
3. **Пример транзакции в маркетплейсе?** Создание заказа, его позиции и списание товара должны пройти вместе; иначе появляется неполный заказ или неверный остаток.
4. **Что обеспечивают атомарность и изоляция?** Атомарность — все изменения применяются или все отменяются. Изоляция — параллельные транзакции не видят промежуточных изменений друг друга.
5. **Что такое функция PostgreSQL и что даёт PL/pgSQL?** Это хранимый вызываемый код; PL/pgSQL добавляет переменные, условия, циклы, запросы в переменные и возврат результата.
6. **Как обработать ошибку и прервать выполнение?** Выполнить `RAISE EXCEPTION`; изменения текущего оператора откатываются.
7. **Что такое триггер и на какие события срабатывает?** Это автоматический вызов функции при `INSERT`, `UPDATE` или `DELETE`.
8. **`BEFORE`/`AFTER`, строка/оператор, `NEW`/`OLD`?** `BEFORE` срабатывает до изменения, `AFTER` — после; `FOR EACH ROW` — для каждой строки, `FOR EACH STATEMENT` — один раз на запрос. `NEW` — новая строка, `OLD` — старая.
9. **Для чего применяют триггеры?** Для аудита, проверок и пересчёта зависимых значений; здесь они записывают историю цены и обновляют средний рейтинг.
10. **Плюсы и минусы логики в СУБД?** Плюсы — общие гарантии целостности и меньше пересылки данных. Минусы — сложнее отлаживать и тестировать, есть привязка к СУБД и дополнительная нагрузка на сервер.
